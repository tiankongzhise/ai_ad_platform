## 三、新发现问题（本轮审查）

### 🔴 P0 — 阻断性问题（4 个）

---

#### [N-P0-1] SECRET_KEY 默认弱密钥

**文件**：`backend/app/core/config.py:38`
**问题**：`SECRET_KEY: str = "your-secret-key-change-in-production"` — 如果生产环境忘记配置环境变量，JWT Token 可被伪造，导致任意用户身份冒充。

**影响范围**：全站安全

**修复方案**：
```python
@field_validator('SECRET_KEY')
@classmethod
def validate_secret_key(cls, v: str) -> str:
    if v == "your-secret-key-change-in-production" and not os.getenv("DEBUG"):
        raise ValueError("SECRET_KEY must be changed in production!")
    return v
```

# 当前（错误）

**影响范围**：数据精度丢失，计算结果错误

### 🟠 P1 — 严重问题（8 个）

---

#### [N-P1-1] JWT 黑名单未集成到 Token 验证流程

**文件**：`backend/app/core/security.py` + `backend/app/core/tenant.py`
**问题**：`verify_access_token` 只验证签名和过期，不检查 Redis 黑名单中的 `jti`。`redis_client.py` 已实现 `is_token_blacklisted(jti)` 但未被调用。

**影响**：用户登出后 Token 仍可使用，直到过期

---

#### [N-P1-2] Redis 连接池非线程安全（懒初始化竞态）

**文件**：`backend/app/core/redis_client.py:28-38`
**问题**：`get_redis()` 使用全局变量 + `if None` 检查，asyncio 环境中多个协程可能同时创建多个连接池实例。

**修复方案**：
```python
_redis_lock = asyncio.Lock()

async def get_redis():
    global _redis_pool
    async with _redis_lock:
        if _redis_pool is None:
            _redis_pool = redis.asyncio.ConnectionPool(...)
    return redis.asyncio.Redis(connection_pool=_redis_pool)
```

**文件**：`frontend-web/src/components/AttributionConfirm/index.tsx:227`
**问题**：`ArrowRightOutlined` 的 import 语句在文件末尾而非顶部。某些打包工具或严格配置下可能导致运行时错误。

---

#### [N-P1-4] 前端 ContextLink 组件 Button 嵌套 Link（无效 HTML）

**文件**：`frontend-web/src/components/ContextLink/index.tsx:41-53`
**问题**：当 `button=true` 时，`<Button>` 内嵌套 `<Link>`，违反 HTML 规范（`<a>` 不可嵌套在 `<button>` 内）。

```tsx
// 当前（错误）
<Button onClick={handleClick}>
  <Link to={buildUrl()}>{children}</Link>  {/* <a> inside <button> */}
</Button>

// 应改为
<Link to={buildUrl()}>
  <Button type={type === 'primary' ? 'primary' : 'default'} icon={<ArrowRightOutlined />}>
    {children}
  </Button>
</Link>
```

## 七、架构层面评价

### 7.1 后端架构

**优点**：
- FastAPI + SQLAlchemy 2.x async 配置规范，连接池参数合理
- 多租户 ContextVar 实现已修复，并发安全
- Redis 功能封装完善（OAuth State、同步状态、黑名单、缓存）
- 异常体系设计合理，覆盖常见业务场景
- Celery 异步任务集成良好（广告同步、报表生成）

**待改进**：
- Mock 层与 ORM 层完全隔离，无法端到端测试
- 租户隔离不彻底（analytics/demo 硬编码租户 ID）
- 自动 commit 策略可能导致非预期行为
- 自定义异常字段在 handler 中丢失

### 7.2 前端架构

**优点**：
- 清晰的分层结构（API → Store → Pages → Components）
- Zustand 状态管理使用得当，persist 中间件合理
- Token 刷新锁机制设计合理
- 组件复用性好（RoiCard、TrendChart、EmptyState）
- ECharts 集成专业，useMemo 优化良好

**待改进**：
- 前后端类型定义多处不一致（RegisterRequest、LoginResponse、DashboardMetrics）
- Token 双写机制（localStorage + zustand persist）有状态不一致风险
- 路由守卫逻辑有竞态和闪烁问题
- 错误处理方式不统一（有的用 message.error，有的用 console.error）
- 部分 useEffect 依赖数组不正确

### 7.3 关键风险

1. **前后端对齐率仅 62%**：7 个后端接口缺失直接影响 CRM 核心流程和 Analytics 交叉分析
2. **安全配置缺陷**：SECRET_KEY 默认值 + JWT 黑名单未集成 + OAuth state 降级
3. **Mock → 生产切换风险**：Mock 层与 ORM 层完全隔离，切换时数据结构可能不兼容
4. **测试覆盖不足**：后端仅 2 个测试文件，前端无测试
